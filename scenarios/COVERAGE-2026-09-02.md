## Beacon periodicity detail (task 2)

Agent built with `SERVER=operator-host:8444` (the beacon endpoint listens
on **8444** by design — `the server configuration` forbids sharing 8443 with the
mTLS listener), run with `-transport https -sleep 15s -jitter 5` (flags
override embeds). 19 Sysmon EID3 events (rat-agent.exe → operator-host,
dst-port 8444, Initiated true) from 01:39:36 to 01:44:05; 18 inter-event
deltas in [14.47, 15.62] s, mean 14.97 s — the 5 % jitter window is
[14.25, 15.75], so every observed poll is in-band. The Sigma-2.0
correlation `2be95732` (count ≥ 8 / 10 min, group-by Image) has its data
requirement met with ~5× headroom at steady state. Interval regularity
(stdev across deltas ≈ 0.4 s) is the high-confidence beacon signature.

## Detached launch test (task 3, owner's open question)

`cmd /c start "" C:\\labs\rat-agent.exe` over ssh is **NOT a reliable
alternative** to the orphan-ssh pattern on this VM:
- Attempt 1: process created (EID1 01:45:00.858, parent cmd.exe) but
  exited ≤ 10 s with zero network attempts (no EID3, no auth on server).
- Attempt 2: survived ≥ 7 s, authenticated once (session f1f178bb, pid
  9236), then vanished < 60 s (session flipped to disconnected, process
  gone, taskkill found nothing).
Conclusion: keep the plain foreground-ssh orphan run as the only
documented launch method; `powershell Start-Process` (known-dead) and
`cmd /c start` (flaky-dying) both fail the "survives and stays
connected" bar.

## Lab findings (config/tooling — owner follow-up, not touched by this run)

1. **HKCU registry writes are invisible to the lab Sysmon config.** The
   deployed `sysmon-lab-config.xml` includes
   `<TargetObject condition="begin with">HKCU\SOFTWARE\…\Run</TargetObject>`,
   but reg writes under HKCU produce NO EID12/13 at all (canary
   `CanaryDiag2026` write to the Run key: no event; HKLM TaskCache
   includes DO fire). Likely cause: Sysmon renders the target under
   `HKU\<SID>\…`, which `begin with HKCU\` never matches. Fix: add
   `HKU\*\SOFTWARE\Microsoft\Windows\CurrentVersion\Run` (or a
   `contains` condition) for EID 12/13. This made SC-03's `c3b6008a` and
   contributes to SC-11's `9e938f81` misses.
2. **Typo in the same config:** `\ms-settings\ShellOpen\command` should
   be `\ms-settings\Shell\Open\command` (missing `\`) — the ms-settings
   hijack point is not captured either (EID13 ms-settings count: 0
   despite two reg adds). The Sigma rule itself is correct.
3. **Windows Defender (real-time, default policies) blocked two runbook
   procedures pre-execution** — both are honest defensive-control wins to
   carry into the debrief: certutil `-urlcache` download →
   Trojan:Win32/Ceprolad.A; AMSI `amsiInitFailed` one-liner →
   Trojan:PowerShell/PsAttack.A (block action made CreateProcess return
   ACCESS_DENIED to the agent). AV detection events (Defender
   Operational EID1116/1117) are the coverage evidence; Sysmon saw
   nothing because the processes never existed.
4. **transfers.attack_tag is T1005** for downloads; mappings.yaml, the
   runbooks, and the scenario_backed entry declare T1105. Also the
   transfers row does not persist sha256 (live log line only). Reconcile
   either the tag mapping or the docs.
5. **No EID 4104 script-block logging** on the reference VM (PS
   Operational log carries only engine lifecycle events). SC-07's
   premise needs Group Policy `ScriptBlockLogging → Enable` (or accept
   that only "suspicious" content auto-logs).
6. **OpenSSH sshd grants range-user a High-integrity token** on this VM —
   there is no filtered token for UAC-bypass scenarios to elevate from.
   SC-11 needs a non-elevated launch context (e.g. RunAs / scheduled
   task with /rl limited as the shell parent) to demonstrate the jump.
7. **Session-0 quirk stack** (all reproducible, all worked around):
   schtasks silently no-ops .bat actions (powershell actions work);
   `certutil -urlcache` needs Defender-off or an interactive context to
   even attempt the fetch; long-running ConPTY shells left open seem to
   degrade the agent's session-0 spawn reliability over tens of minutes
   (fork/exec ACCESS_DENIED until agent restart — observed once, 02:34,
   not root-caused, not reproduced after the restart).
